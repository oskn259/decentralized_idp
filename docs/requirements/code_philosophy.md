## コーディング観点でのメンテナンス性向上

指定された要件を満たすことはいわゆる機能要件であり、メンテナンス性に関わる非機能要件の一環として、ソフトウェアのメンテナンス性向上を考える。
コードというのは機械への命令を人間が読めるために発明されたのであって、コーディングにおいて実施されるメンテナンス性向上として、その可読性の向上を重要な指標として位置付ける。
具体的な定義として、以下の項目を可読性とする。

### AI時代であってもコードは人間が読むもの

昨今は指示さえ出せばAIが大抵のコードは出力してくれますし、その気になればコードなんて見ないことは可能でしょう。
しかし製品としてそれをリリースするなら、将来のメンテナンスを可能にしておかねばなりません。
例えばバグの報告から調査をして修正する、という流れにおいて、AIに調査させたバグの原因レポートは二次情報です。
参考情報として活用するのは良いですが、それを自分でコードを見て裏取りをする必要があります。
またテストを充実させればコードを見なくても良いという論もありますが、AIで書かせたものの検証をするためにAIに書かせるという自己依存に陥っています。
コードは人間が読んで理解できるものでなくてはなりません。

### 意味のある単位でできるだけ小さく分割

巨大なコードは人間には解読できません。　
また、単に小さく区切るだけでも参照先が増えるだけで理解の助けになりません。
人間は既知の概念の組み合わせによって大きな事柄を理解します。
大きな事柄は既知の概念の組み合わせによって表現し、子側の概念もまた、既知の概念の組み合わせによって表現されるべきです。
単に細かく区切るのではなく、既知の概念として表現できることが重要です。
ループの中に try/catch や条件分岐を重ねません。1要素の処理は関数に切り出し、ループは map と filter で書きます。

### 新規の定義を控える

コードを書いたりその指示をエージェントにしたとしても、1ヶ月後の自分は記憶が蒸発しています。
何も知らない人間が再度読んで理解できるものでなくてはなりません。
読むにあたって先に説明が必要であるのは読み手の理解の障害であり、作成者が思い出す時間のコストです。
既知の概念の組み合わせでできる限り対応し、どうしても必要もしくは有用性が高いものに限り、新規の定義を行います。

### 平易に、短く

人間は長い文章や難しい文章を読めません、読めるフリをしているだけです。
少しのパフォーマンス向上よりも、人間にとっての読みやすさが圧倒的に大事です。
コードにしろコメントにしろ、難しい表現は避け、真に必要な記載のみに絞って記載します。
見ればわかるようなことをコメントにしたりドキュメントで長々と書くことは逆に複雑さを増しています。

### 共通化とは省略ではなく、将来にわたってそれらが同じであるという制約

似たコードを共通化することでうまく分割できたと思うかもしれません。
しかし共通化とは、将来にわたってそれらが同一であるべきだ、という制約の導入です。
一方を変えたのならば当然もう一方も変わらねばならない、という状況においては正当です。
しかし単にコードが似ているから共通化したいというのは、たまたま今似ている本来的に別のものに不要な制約を導入しています。

### コードやドキュメントは「成果物」である

どういう経緯でそうしたのか、前はこうだった、という制作過程の情報はログであり成果物とは関係がない。
そうした履歴を保管するのは例えばgit等の外部ツールであり、コードやドキュメントは現状の成果以外の意味を持たない。
理解や運用における罠を回避するためにどうしても必要な情報のみ記載しても良い。

### ディレクトリ構造

DDDをベースに、しかし厳密には従わない形で、ドメインをまとめて表現したり依存を簡素に表現します。
フレームワーク等で求められるものに加え、以下のようなディレクトリを用意します。

- domain: 依存関係をdomain内部のみで完結させたビジネスロジック
  - entity: repositoryによって管理されるデータレコードの定義
  - usecase: domainの外に提供する機能。各種実装を与えて使用
  - service: ビジネスロジック本体
  - repository: entity管理のインターフェース
  - infra: repository以外の外部接続インターフェース
  - value: 各種データ型
- infra: domain/repository と domain/infra の実装
- helper: domainとはいえない一般的な機能群
